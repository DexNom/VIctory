# CPU waits and GPU queue timestamps

The frame line, window caption and optional HUD label CPU completion waits
in milliseconds per presented frame. They no longer label this time as GPU
utilization. The synchronous path measures the blocking event wait, excluding
command submission and bookkeeping. In relay mode the CPU may also be waiting
for another CPU thread to publish GPU-written data. This is accumulated thread
time, not an exclusive partition of the frame; it can overlap other work.

## Optional GPU sampling

Build the diagnostics programs and enable queue timestamps in PowerShell:

```powershell
cargo build --locked --release -p victory --features diagnostics --bins
$env:VICTORY_GPU_QUEUE_TIMING = '1'
$env:VICTORY_DEBUG_HUD = '1'
```

Then launch the runtime normally. This switch is off by default and independent
of `VICTORY_GPU_TIMING`, which times individual commands and forces synchronous
per-list execution. Queue sampling leaves the existing submission grouping,
completion fence signals and CPU waits in place.

Two GPU timestamp markers bracket each main direct-queue submission, including
its runtime preludes and buffer comparisons. The timestamps are resolved into
a private readback buffer. The CPU polls the existing completion fence and
reads the buffer only after that submission completes. Up to 32 samples can be
in flight; at capacity or on allocation failure, the submission runs without a
sample instead of waiting for one. Completed slots are reused.

The log and HUD distinguish:

- **CPU completion wait, ms/frame:** CPU wall time in the submission completion
  waits, averaged over presents. Background worker waits are not included.
- **GPU queue, ms/batch:** mean elapsed GPU timestamp interval over completed
  sampled batches in this observation window. The report includes their total
  time and completed, pending, skipped and invalid counts.
- **Off / unavailable / n/a:** disabled sampling, unavailable queries, or no
  completed valid samples. Missing measurements are not reported as zero work.

A completed batch may have been submitted in an earlier frame. The GPU total
is therefore not divided by the current window's frame count or reported as
a utilization percentage. These intervals describe work bracketed on this
queue, including stalls within it; they are not whole-device active time.
Auxiliary upload/readback submissions and the separate relay are outside this
sample. The existing fence-based queue-clock estimate is also labeled as an
estimate of outstanding work, not device utilization.

Sampling adds two marker lists and query resolution per sampled batch, so
compare overhead before using it for performance decisions. Record the commit,
adapter, driver, enabled switches, observation duration, and sample coverage.
Do not compare different RT, resolution or cache-warmth settings as a speedup.

## Synthetic regression without a game

```powershell
cargo test --locked -p victory-gpu host::gpu_timing::tests -- --nocapture --test-threads=1
```

The GPU test uses its own direct queue, two 1 MiB copies of generated bytes and
a deliberately closed queue gate. It verifies that unresolved queries stay
pending and a full two-slot pool skips a sample without blocking. After release,
the completed copies are checked byte for byte, samples are counted once and
slots can be reused. Delaying CPU observation preserves the same GPU result.
CPU fence-wait and GPU timestamp times are printed separately; no hardware
performance threshold or expected ratio is asserted. Separate conversion tests
cover fractional ticks, zero frequency, reversed queries and large counters.

For integration coverage, run the GPU tests with `--features diagnostics` and
`VICTORY_GPU_QUEUE_TIMING=1`. `VICTORY_D3D12_WARP=1` selects WARP for a separate
software-adapter run. Tests never need game files or a FidelityFX provider.

Microsoft documents queue timestamp frequency and bottom-of-pipe semantics in
[D3D12 Timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing).
